이 문서는 **코드만 봐서는 보이지 않는 "왜"** 를 남기기 위한 것이다.

저장소의 문서 셋은 역할이 다르다:

| 문서 | 역할 |
|---|---|
| `PRD.md` | **명세** — FR-1~13이 무엇을 요구하는지, 각 FR의 `구현 메모`에 초안과 실제가 갈라진 지점 |
| `CLAUDE.md` | **작업 규칙** — 이 저장소에서 코드를 고칠 때 지켜야 할 것 |
| `docs/개발노트.md` (이 문서) | **경위와 학습** — 어떤 순서로 무엇을 겪으며 만들어졌는지, 각 기능이 무엇을 보고 무엇을 못 보는지 |

## 1. 이 도구가 하는 일 — 한 문단

재무제표와 전표에서 **감사인이 더 들여다볼 곳을 좁혀주는** 스크리닝 도구다.
산출물은 **감사증거도 감사결론도 아니다.** ISA에 근거해 위험 신호를 선별하고 추천 감사절차를 제시할 뿐이며,
판단은 감사인이 한다. 이 원칙이 화면 문구·리포트·코드 주석 전반에 일관되게 박혀 있다.

## 2. 개발 연대기 — 6단계

| 단계 | 시기 | 핵심 사건 |
|---|---|---|
| 1 | 7/23 | Streamlit 프로토타입 → **하루 만에 Next.js로 이관** |
| 2 | 7/24 | 프로덕션 장애 대응 + **파트너 리뷰 반영(전환점)** |
| 3 | 7/27 | 신뢰성 강화 — 가짜 기준서 차단, Benford·MUS 정정 |
| 4 | 7/28 | 감사 실무 완성 — RAG 챗봇, 중요성(320), SUM(450) |
| 5 | 8/11 | 정합성 — 결산일 추정 제거, 샘플 tie-out |
| 6 | 9/2 | 품질 — 회귀 테스트 158건, `page.tsx` 분리, 문서 정리 |

### 1단계 — 스택 교체

첫날 Python/Streamlit으로 만들었다가 같은 날 Next.js로 옮겼다. 배포·API 키 관리·프론트 완성도에서
한계가 명확했고, GitHub↔Vercel 자동배포 흐름이 필요했다.

**프로토타입은 지우지 않고 아카이브로 남겼다** (`app.py`, `src/`, `templates/`). 다만 실행 가능하다고
가정하면 안 된다 — `venv/`는 저장소에 없다.

### 2단계 — 전환점

**사건 A: 배포본에서 기업 검색이 멈췄다.**
DART의 `CORPCODE.xml`(11만 8천 건 ZIP)을 매 요청마다 내려받는 구조였는데, Vercel 서버리스는
실행 10초 제한 + 파일시스템 읽기 전용이라 런타임 캐싱도 불가능했다.
→ **빌드 시점에 JSON으로 만들어 저장소에 커밋**하는 방식으로 전환(`scripts/build-corp-codes.js`).

**사건 B: 스스로 점검하고 세 가지를 고쳤다.** (커밋 `6fc61db` — 이 프로젝트의 분기점)

1. **라운드트립 탐지가 통계적으로 엉터리였다.** 아래 §6에 상세.
2. **명칭이 과장이었다.** "순환거래 네트워크 분석" → "라운드트립(2자간 상계성 거래) 탐지".
   자사 원장 하나로 A→B→C→A 3자 순환을 보는 것은 **구조적으로 불가능**하다(중간 당사자 장부가 없다).
3. **홍보 문구가 사실과 달랐다.** "전수 데이터 자동 부정탐지" → ISA 기반 스크리닝이며 감사증거가
   아님을 명시. "전수"는 **전표 원장을 실제로 업로드한 경우로만** 한정.

### 3단계 — 신뢰성

- **LLM이 없는 기준서를 인용했다** — `ISA 515`, `ISA 541`. 둘 다 실재하지 않는다. → 화이트리스트 가드(§7).
- **MUS 확장계수가 틀려 있었다** — 99%에서 2.0을 썼으나 AICPA 표값은 **1.9**. 표본이 과대 산출되고 있었다.
- **Benford 판정 기준 교체** — 카이제곱은 표본이 크면 사소한 편차도 유의하다고 판정해 대규모 원장에서
  과탐한다. 표본크기에 무관한 **MAD(평균절대편차)** 로 바꿨다.

### 4단계 — 감사 실무의 완성

중요성(ISA 320)이 들어오면서 나머지가 하나로 꿰어졌다. **중요성이 MUS의 허용왜곡금액이 되고,
이상 변동 필터의 금액 게이트가 되고, 미수정왜곡 집계표의 판단 기준이 된다.**

### 5단계 — 정합성

**결산일을 추정하지 않기로 했다.** JE 테스트의 "결산일 임박 전기"가 데이터상 최종 전기일자를 결산일로
추정했는데, 기중 데이터만 올리면 마지막 5일치 정상 전표가 통째로 예외로 잡힌다.
→ 감사인이 직접 입력하게 바꾸고, 추정한 경우에는 라벨에 "추정"을 남겨 근거를 드러낸다.

> 원칙: **감사인의 판단 영역은 감사인에게 돌려준다.**

### 6단계 — 품질

도메인 로직에 회귀 테스트 158건을 붙였다. 테스트를 쓰는 과정에서 **잠복 버그 3건**이 드러났다(§8).

## 4. 데이터 입력 3경로

| 경로 | 대상 | 처리 위치 | 주의 |
|---|---|---|---|
| DART 검색 | 상장기업 | 서버 (키 필요) | `parseTagValue: false` 필수 |
| 엑셀 템플릿 | 비상장, 정형 | **브라우저 전용** | 고정 스키마 |
| AI 이미지/PDF 인식 | 비상장, 비정형 | 서버 → Upstage | 평평한 스키마 |

**`parseTagValue: false`가 왜 필수인가**: 이 옵션이 없으면 `corp_code`의 앞자리 0이 숫자로 변환되며
조용히 손상된다(`"00126380"` → `126380`). 오류가 나지 않고 조용히 틀리기 때문에 특히 위험하다.

**엑셀 스키마를 고정한 이유**: 회사마다 계정과목 표기 관행이 달라 자유 형식 파싱은 신뢰할 수 없다.
템플릿 생성기와 파서가 같은 스키마 상수(`excelTemplate.ts`)를 공유한다.

**AI 인식 결과는 교차검증한다**: 인식된 영업이익·당기순이익을 손익계산서 산식으로 재계산해
비교하고, 허용오차를 넘으면 ⚠와 빨간색으로 경고한다.
`영업이익 = 매출액 − 매출원가 − 판관비`, `당기순이익 = 영업이익 + 영업외수익 − 영업외비용 − 법인세비용`

## 5. 계정명 매칭의 두 가지 함정

출처마다 계정 표기가 달라 `ACCOUNT_ALIASES`로 공백 무시 부분일치 검색을 한다. 함정이 둘 있다.

**① 합계행 후보를 배열 앞에 둬야 한다.**
`유동자산`만 찾으면 `기타유동자산`이 먼저 걸려 유동비율의 분자가 엉뚱해진다.

**② 영업외수익·영업외비용은 합산해야 한다.**
DART는 이 둘을 한 줄로 주지 않고 `기타수익`/`금융수익`처럼 쪼개서 준다. 첫 매칭 하나만 집으면
나머지가 통째로 누락된다. 그래서 이 둘만 **"합계행이 있으면 그 행, 없으면 구성계정 합산"** 으로
읽는다(`ADDITIVE_ACCOUNTS`). 한 행이 여러 패턴에 걸려도 중복 합산되지 않도록 처리했다.

비슷하게 쪼개져 오는 개념을 새로 다룰 때는 이 목록에 추가한다.

## 6. 스크리닝 모델 5종 — 무엇을 보고 무엇을 못 보나

| 모델 | 필요 데이터 | 임계 | 못 보는 것 |
|---|---|---|---|
| Benford | 전표 | MAD 기반 | 표본 30건 미만이면 판정 안 함 |
| Beneish M | 재무제표 + **현금흐름표** | −1.78 | CF 없는 AI 인식 경로에선 계산 불가 |
| Altman **Z'** | 재무제표 | 2.9 / 1.23 | — |
| RSF | 전표 | 3배 | 계정 내 상대 비교뿐 |
| 라운드트립 | 전표 + 거래처 | 30일 / 5% | **3자 이상 순환** |

### Altman은 Z가 아니라 Z'다

원래 Z-Score의 X4는 자기자본의 **시가총액**을 쓴다. 이 도구의 주 사용처인 비상장기업에는 시가가
없어 계산 자체가 불가능하다. 그래서 자기자본을 **장부가액(자본총계)** 으로 대체한 **Z'-Score**
계수를 쓴다: `0.717·X1 + 0.847·X2 + 3.107·X3 + 0.42·X4 + 0.998·X5`

> `GET /api/stock-price`(네이버 증권)는 Altman이 아니라 **PER·PBR 계산용**이다. 종목코드가 있는
> 상장사 경로에서만 버튼이 노출된다.

### Benford 판정을 MAD로 하는 이유

카이제곱 통계량은 표본크기에 비례해 커진다. 같은 편차 비율이어도 원장이 10배 크면 카이제곱도
약 10배가 되어 "유의한 이상"이라고 말하기 시작한다. **MAD는 비율 기반이라 표본크기와 무관하다.**
카이제곱 값도 참고용으로 함께 표시하되, 판정은 MAD로 내린다.

첫 두 자리(10~99) 검정은 구간이 90개라 표본 300건 이상일 때만 수행한다.

### 라운드트립 — 재설계의 회계적 근거

**옛 로직**: 전표 라인을 차변>대변 부호로 짝지어 거래 방향을 추정.

**무엇이 틀렸나**: 차변·대변은 **복식부기의 기록 규칙이지 경제적 거래 방향이 아니다.**
`매출채권 차변`은 "샀다"가 아니라 "팔아서 받을 돈이 생겼다"이고, `현금 대변`은 "팔았다"가 아니라
"돈이 나갔다"이다. 같은 차변이 계정에 따라 정반대를 뜻하므로 부호만으로는 판별할 수 없다.

그 결과 **매출채권 회수, 매입채무 지급, 차입금 상환, 감가상각은 물론 한 분개의 두 다리까지**
라운드트립으로 잡혔다. 샘플 42줄에서 25건이 걸렸고 대부분 오탐이었다.

**새 로직**: 계정의 **성격**으로 경제적 방향을 판정한다.
- 판매 = 수익 계정이 대변에 잡힌 줄 (단, `매출채권`·`매출원가` 제외)
- 구매 = 매입·자산취득·비용 계정이 차변에 잡힌 줄
- **정산계정 제외** — 매입채무·미지급·차입·현금·예금, 그리고 이자·법인세·금융비용 같은 순수 재무손익

여기 깔린 통찰은 이것이다: **매출채권 회수는 "거래"가 아니라 "결제"다.** 라운드트립은 실질 없는
*거래*를 만들어내는 행위이므로, 봐야 할 것은 수익·비용을 **인식하는 순간**이지 그 뒤의 결제 단계가 아니다.

추가 안전장치 둘: 같은 전표번호끼리는 매칭 제외(자가매칭 차단), 매출 1건은 매입 1건에만 1:1 매칭(중복 보고 방지).

**결과**: 25건 → 1건. 남은 1건은 샘플에 의도적으로 심어둔 진성 건이다(거래처명 "순환에너지㈜",
2/10 매출 500만원 ↔ 2/13 매입 500만원, 3일 간격).

> **탐지 = 부정 확정이 아니다.** 실제로 팔고 실제로 다른 물건을 사왔을 수도 있다. 감사인이 거래
> 실질(운송 증빙, 대금 결제, 사업 목적)을 확인해야 할 **예외항목**이라는 것이 이 도구가 하는 말의 전부다.

## 7. AI를 쓰는 네 곳과 각각의 방어장치

Upstage API 키 하나로 세 종류의 엔드포인트를 쓴다.

```
UPSTAGE_API_KEY
  ├─ /v1/chat/completions       → 체크리스트, 공시요약, 챗봇 답변  (solar-pro2)
  ├─ /v1/embeddings             → 챗봇 RAG 검색                  (embedding-query/passage)
  └─ /v1/information-extraction → 재무제표 이미지·PDF 인식        (information-extract)
```

### Solar 호출 구조

호출 시 세 가지를 함께 보낸다.

| | 역할 |
|---|---|
| `system` 프롬프트 | 직무 지시서. "너는 한국 회계법인의 시니어 감사인이다" — 매번 동일 |
| `user` 프롬프트 | 실제 안건. 위험 신호 목록 / 공시 제목 목록 — 매번 다름 |
| `response_format.json_schema` | 보고서 양식. 자유 서술 대신 정해진 필드로 답하게 강제 |

`upstageChat.ts`에 두 함수가 있다. `callSolarChat`(자유 서술, 챗봇용)과
`callSolarChatJSON`(스키마 강제, 체크리스트·공시요약용).

**모든 LLM 호출이 이 파일 하나를 거친다.** Upstage는 OpenAI Chat Completions와 동일한 요청·응답
형태라, 다른 제공자로 바꾸려면 `ENDPOINT`와 `MODEL` 상수 두 개만 고치면 된다.

### 공시요약 — 목록을 통째로 1회 호출

공시 10건을 10번 부르지 않고 번호를 매겨 한 번에 보낸다. 크레딧 종량제이므로 비용이 1/10이다.

**응답으로 제목을 돌려받지 않는다. 번호만 받는다.** LLM이 한글을 재생성하면서 특수문자(`ㆍ` 등)가
깨지기 때문이다. 정확한 제목·날짜·접수번호는 이미 DART에서 받아 우리가 갖고 있으므로,
LLM에게는 **판단만**(쟁점인가, 왜) 시키고 사실 데이터는 번호를 키로 우리가 다시 붙인다.

> 반복되는 원칙: **AI에게는 판단만 맡기고 사실 데이터는 우리가 보관한다.**
> 공시 제목, ISA 인용, RAG 인용 세 곳에서 같은 패턴이 나온다.

### RAG 챗봇 — 근거가 없으면 부르지 않는다

```
질문
 ├─ 1. 질문을 4096차원 좌표로 변환            (임베딩 API 1회)
 ├─ 2. 코퍼스 28개 좌표와 코사인 유사도 계산   (API 호출 없음, 메모리 계산)
 ├─ 3. 최고 점수 < 0.28  → 기권. Solar 호출 안 함
 │                        + 아깝게 떨어진 후보 3개와 임계값을 함께 반환
 ├─ 4. 통과하면 해당 문서 본문을 프롬프트에 첨부 → Solar 호출 1회
 └─ 5. 답변 + 인용. 인용을 누르면 실제로 근거로 넘긴 요지 원문을 보여준다
```

**3번이 환각 방어의 1단계다.** 걸러내는 것이 아니라 **지어낼 기회를 주지 않는다.**

**코퍼스**(`data/standards-corpus.json`)는 감사기준서 28개의 요지와 임베딩이 함께 든 2.2MB 파일이다.
문서 임베딩은 `scripts/ingest-standards.js`로 **빌드 시점에 한 번만 계산해 커밋**한다(구워둔다).
매 질문마다 29번 호출할 것을 1번으로 줄이기 위해서다.

> **코퍼스에는 기준서 원문이 들어 있지 않다.** `standards-source.json` 첫 줄에 명시돼 있듯
> **자체 정리 요지**다. 기준서 원문은 저작물이므로 복제하지 않았고, 그래서 챗봇도 원문을 그대로 뱉지 않는다.
> 조문 번호 단위의 인용은 이 도구가 제공할 수 없는 정보다.

**임계값 0.28의 근거**: 유효한 감사 질문은 0.32~0.51, 무관한 질문(날씨·코딩·요리)은 0.10~0.16으로
분포가 갈렸고, 그 사이 빈 구간에 선을 그었다. 중간값(0.24)보다 높게 잡은 것은 의도적이다 —
**틀린 답보다 침묵이 낫다**는 판단이다.

> **한계**: 정식 실험이 아니라 경험적 보정이다. 라벨링된 질문 세트로 정밀도·재현율 곡선을 그려
> 정한 값이 아니다. 또한 이 값은 Upstage 임베딩 좌표계에 종속되므로, 임베딩 모델을 바꾸면
> **코퍼스를 전부 다시 굽고 임계값도 다시 잡아야 한다.**

### 벡터 DB를 쓰지 않은 이유

문서가 28건 규모다. 가장 비슷한 4개를 고르는 것은 반복문 한 번이면 된다. 벡터 DB를 붙이면
인프라·비용·장애 지점만 늘어난다. 수천~수만 건으로 늘면 그때 pgvector 등을 검토한다.

### ISA 인용 화이트리스트 — 3단 가드

LLM이 실재하지 않는 기준서를 인용한 사례가 실제로 관측됐다(`ISA 515`, `ISA 541`).
회계 전문가가 보는 화면에 가짜 기준서가 뜨면 도구 전체의 신뢰가 무너지므로 3단으로 막는다.

1. **단일 진실 공급원** — `isaStandards.ts`의 `ISA_STANDARDS`(28개)를 서버와 클라이언트가 공유
2. **프롬프트 제한** — 허용 목록을 프롬프트에 넣고, 적절한 것이 없으면 빈 문자열을 반환하게 지시
3. **응답 차단(실제 방어선)** — `resolveIsaReference()`가 API 응답 단계와 렌더링 단계에서
   두 번 검사. 통과하지 못하면 "근거 기준서 미확인 — 감사인이 직접 확인 필요"로 대체하고 클릭도 막는다

**프롬프트는 부탁이고, 후처리 필터가 방어선이다.**

번호 인식은 **앞뒤에 숫자가 더 붙지 않은 3자리만** 인정한다. 그렇지 않으면 `ISA 2400`(검토업무
기준서 — 감사기준서가 아니다)이 `240`으로 잘려 통과한다.

### 제3자 전송 동의 게이트

Upstage로 데이터를 보내는 **모든** 경로(자동인식·체크리스트·공시요약·챗봇)는
`aiConsent.ts`의 `ensureThirdPartyAiConsent()`를 먼저 호출해야 한다. 새 AI 기능을 추가할 때
이 호출을 빠뜨리면 게이트에 구멍이 생긴다.

**감사대상 회사명은 LLM 프롬프트에 넣지 않는다.** 체크리스트는 위험 신호 텍스트만,
공시요약은 공시 제목만 보낸다.

## 8. 기밀성 설계

| 데이터 | 어디까지 나가나 |
|---|---|
| 전표·시산표 (거래 단위 원장) | **브라우저 메모리에만.** 서버 전송 없음, localStorage 기록도 없음 |
| 요약 재무제표 | localStorage. 서버 저장은 선택(환경변수 설정 시) |
| 업로드 엑셀 파일 | 브라우저에서만 파싱. 서버로 전송하지 않음 |
| 생성된 조서(PDF/Word) | 브라우저에서 생성해 바로 다운로드. 서버에 남지 않음 |

**서버 저장은 선택 사항이다.** `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`가 있으면 Supabase에
저장하고, 없으면 자동으로 localStorage 폴백으로 동작한다. **환경변수 없이도 전 기능이 동작하는
것이 기본값**이다.

서버 저장을 켰을 때의 설계:
- 감사 이벤트는 **append-only**. `UPDATE`/`DELETE`를 **DB 트리거로 원천 차단**해
  서버 키(service_role)로도 과거 기록을 조작·삭제할 수 없다
- 요청 삭제는 hard delete가 아니라 `deleted_at` **soft delete** + 삭제 이벤트 기록
- RLS는 **켜기만 하고 정책은 두지 않는다** — 서버가 service_role로만 접근(RLS 우회)하므로,
  RLS를 켜는 목적은 anon/public 키의 직접 접근 차단이다

## 9. 알아두면 좋은 함정

**샘플 데이터가 두 종류다.**

| 샘플 | 라운드트립 |
|---|---|
| `sample-data/전표테스트_샘플.xlsx` (파일 업로드) | **1건 탐지** |
| "파일 없이 샘플 데이터로 체험하기" 버튼 (`sampleData.ts`) | **0건** |

원클릭 샘플은 8/11에 **전표→시산표→재무제표가 서로 대사(tie-out)되도록** 재구성되면서
라운드트립 거래가 빠졌다. **라운드트립 기능을 시연하려면 xlsx 파일을 업로드해야 한다.**

**개발 서버는 반드시 `.claude/launch.json`의 `web-app`으로 띄운다.**
`src/lib/dart.ts`의 디스크 캐시 경로가 `process.cwd()` 기준이라, 저장소 루트에서 그냥
`npm run dev`를 하면 캐시가 엉뚱한 곳에 조용히 저장된다. `scripts/start-dev.js`가
`process.chdir()`로 `web/`로 이동한 뒤 Next CLI를 실행하는 이유다.

**`master`에 push하면 Vercel이 프로덕션에 자동 배포된다.** 배포를 통제하는 유일한 지점은 push다.
작업은 브랜치에서 하고(브랜치 push는 프리뷰 배포), 검토 후 병합한다.

## 11. 이 도구가 못 하는 것

솔직하게 적어둔다. 이걸 모르고 쓰면 위험하다.

- **감사증거가 아니다.** 스크리닝 지표이며, 결론은 감사인이 내린다.
- **3자 이상 순환거래는 탐지할 수 없다.** 자사 원장만으로는 구조적으로 불가능하다.
- **DART·AI 인식 경로는 전수가 아니다.** 요약 재무제표만 제공되므로 전표 단위 탐지
  (Benford·RSF·라운드트립·JE 테스트)가 동작하지 않는다.
- **대용량 전표는 범위 밖이다.** 전표 1만 건 이하 규모를 상정했다.
- **산업평균 비교(FR-2.4)는 비활성이다.** `industry.ts` 로직은 완성돼 있으나
  `data/listed-industry.json`이 저장소에 없어 항상 "준비되지 않았습니다"를 반환한다.
  DART 키로 `node scripts/build-listed-industry.js`를 1회 실행해 인덱스를 만들어 커밋하면 켜진다.
- **Beneish M-Score는 현금흐름표가 없으면 계산되지 않는다.** AI 인식 경로가 여기 해당한다.
- **챗봇은 조문 단위로 답할 수 없다.** 코퍼스가 원문이 아닌 자체 요지이기 때문이다.
- **임계값들은 경험적으로 정한 값이다.** RSF 3배, 라운드트립 30일/5%, RAG 0.28 모두
  통계적 최적화 결과가 아니라 실무 통용값 또는 관찰 기반 보정값이다.
